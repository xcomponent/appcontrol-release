    Installer sans ambiguïté : registre, réseau, gateway et agents¶

    Le schéma de base¶

    Navigateur ── HTTPS 443 ── Route web (réencryptée) ── interface:8080 ── backend:3000
                                                                            │
Agent externe ── WSS 443 sortant ── Route gateway (passthrough) ── gateway:4443 │
                                                                 └─ WSS/mTLS┘
                                                                  backend ── PostgreSQL:5432

    La gateway est incluse. Il n'est pas nécessaire d'en installer une deuxième pour le premier agent externe. Deux noms DNS pointent vers le routeur OpenShift : appcontrol.apps.cluster.banque et gateway-appcontrol.apps.cluster.banque. « Externe au cluster » ne signifie pas « exposé à Internet » : ces noms peuvent rester accessibles uniquement sur le réseau interne de la banque.

    Les agents initient la connexion persistante vers la gateway. Les commandes reviennent sur cette connexion ; AppControl n'ouvre pas une connexion entrante vers chaque serveur agent. Une gateway de zone supplémentaire n'est utile que si la segmentation réseau du client l'impose.

    Flux à faire approuver¶

    Source Destination Port Usage
    Poste d'administration API OpenShift Port de leur API, généralement 6443 Installation et recette avec oc/kubectl/Helm
    Nœuds OpenShift Registre interne Généralement TCP 443 Téléchargement des images ; aucun accès GitHub requis si elles sont déjà recopiées
    Navigateur Route web TCP 443 Interface/API/WebSocket utilisateur
    Serveur agent Route gateway TCP 443 Enrôlement puis connexion WSS avec mTLS
    Routeur Interface / gateway TCP 8080 / 4443 Routage interne ; ne pas ouvrir ces ports sur les serveurs clients
    Interface et gateway Backend TCP 3000 Transport interne TLS, gateway authentifiée par mTLS
    Backend PostgreSQL TCP 5432 Base avec vérification TLS
    Pods DNS du cluster TCP/UDP 53 et 5353 selon OpenShift Résolution ; 5353 correspond au DNS après traduction réseau
    Backend Fournisseur SSO/IA TCP 443, optionnel Désactivé par défaut ; destinations explicitement configurées si utilisées

    Cette matrice décrit les flux de contrôle AppControl. Les commandes métier exécutées par un agent peuvent demander leurs propres accès (base, stockage, API interne, etc.) : les qualifier avec les procédures de l’application. Le flux sortant 443 vers la gateway ne remplace pas ces éventuels flux métier.

    Aucune sortie Internet du backend n'est nécessaire pour cette évaluation sans IA/SSO. Les NetworkPolicies limitent la communication aux services attendus. L'accès aux ports frontend/gateway reste ouvert dans leurs règles d'entrée afin d'accepter le routeur : le filtrage des sources clientes relève aussi des règles d'accès au routeur et du réseau bancaire. Ne pas présenter cela comme une restriction par adresse utilisateur déjà configurée.

    Mise à jour d’une installation existante : renseigner les destinations de son SSO/IA avant d’appliquer ce chart. Le nouveau défaut coupe leurs sorties HTTPS s’il n’est pas configuré ; la connexion locale de l’évaluation reste indépendante.

    Pour activer des destinations HTTPS : networkPolicy.backendHttpsCIDRs dans les valeurs Helm. Un changement d'adresse du fournisseur impose leur mise à jour. L'option allowAnyBackendHttps=true reste explicite ; elle n'est pas requise ici. Les politiques standard Kubernetes n'offrent pas à elles seules un filtrage FQDN.

    La Route gateway doit rester en passthrough TLS : pas de terminaison TLS ni inspection intermédiaire qui supprime le certificat client. Vérifier que le réseau autorise WebSocket et une connexion longue. Un proxy authentifié imposé aux agents nécessite une qualification spécifique ; il n'est pas couvert par ce test.

    D'où viennent les images ?¶

    Au 8 octobre 2026, le téléchargement anonyme du dépôt de développement ghcr.io/fredericcarre/appcontrol-backend fonctionne ; l'accès anonyme au dépôt ghcr.io/xcomponent/appcontrol-backend retourne HTTP 401. Ne pas donner un tag historique comme s'il contenait les corrections de cette branche. Les images qualifiées dans le Sandbox se trouvent dans son registre interne, non accessible depuis le cluster client. Le kit final ed757ba inclut les archives OCI des cinq images exactes : leur import ne nécessite aucun accès au Sandbox.

    Le kit final utilise le chemin hors ligne ci-dessous. Les autres options restent possibles :

    1. Registre éditeur autorisé : remettre les cinq références par digest et les modalités d'authentification. Un imagePullSecret déjà créé dans le projet peut être passé avec --image-pull-secret NOM. Ne pas changer la visibilité d'un dépôt pour résoudre une difficulté d'installation.
    2. Registre interne, recommandé : copier une fois les images approuvées, puis installer uniquement depuis le registre bancaire. Le script transfer-images.py conserve les digests et génère le lock de l'installateur.
    3. Réseau fermé : exporter des archives OCI depuis un poste autorisé, les transférer par le canal convenu puis les importer dans le registre interne.
    4. Base bancaire imposée : copier nos artefacts compilés sur cette base avec docker/corporate/. Scanner les nouvelles images et produire leurs nouveaux digests ; les anciens scans ne s'y appliquent plus.

    Les cinq images incluent l'agent de recette ; seules les quatre images de services sont requises par l'installateur. Les agents sur VM peuvent utiliser le binaire.

    # Prérequis : Skopeo et accès aux registres via skopeo login (mot de passe hors argv).
# source.lock.json : quatre services + éventuellement agent, tous par digest.
# Sans --execute, ces commandes affichent seulement le plan.
python3 scripts/qualification/transfer-images.py mirror \
  --lock source.lock.json --target-prefix registre.banque/appcontrol \
  --version VERSION --output-lock images.lock.json --execute

# Sur le poste disposant de l'accès au registre source :
python3 scripts/qualification/transfer-images.py export \
  --lock source.lock.json --archive-dir images-oci --execute
# Après transfert du lock et des archives, sur le réseau bancaire :
python3 scripts/qualification/transfer-images.py import \
  --lock source.lock.json --archive-dir images-oci \
  --target-prefix registre.banque/appcontrol --version VERSION \
  --output-lock images.lock.json --execute

    Ne pas désactiver la vérification TLS du registre. Installer sa CA dans la configuration de confiance de Skopeo et des nœuds, selon la procédure plateforme. Les commandes d'import doivent être validées sur le registre cible ; aucun registre client n'était accessible lors de cette qualification.

    La commande à dérouler chez le client¶

    Copier scripts/qualification/client.example.json en client.json et renseigner les noms de projet, de contexte, les deux Routes et les chemins. Ce fichier ne contient aucun mot de passe. Les chemins relatifs sont résolus depuis son dossier.

    python3 scripts/qualification/install.py --config client.json --preflight-only
python3 scripts/qualification/install.py --config client.json

    Si le registre exige un secret, ajouter --image-pull-secret NOM_DU_SECRET aux deux commandes. Les paramètres CLI priment sur le fichier. Le chart conserve deux anciennes révisions de chaque Deployment (global.revisionHistoryLimit=2) afin de limiter les ReplicaSets dans les projets soumis à quota. Prévoir une marge pour les nouvelles révisions et les autres applications du projet ; cet historique est distinct de celui de Helm.

    Conserver le dossier privé pour les mises à jour : les certificats et identifiants y sont réutilisés.

    Enrôlement d'un agent Linux extérieur¶

    1. L'installateur affiche les deux URL et produit agent-ca.crt. Copier uniquement ce certificat public, jamais ca.key, les mots de passe ou le dossier privé entier.
    2. Dans Enrollment, créer un jeton de portée agent, à usage unique et durée courte. Le remettre via le canal sécurisé convenu ; enregistrer sa valeur dans un fichier privé token (mode 0600), sans le mettre dans l'historique du shell.
    3. Installer le binaire Linux correspondant à la version et vérifier son SHA-256. Vérifier aussi son chargement avec appcontrol-agent --version avant de créer le jeton. Le kit officiel utilise MUSL pour Linux AMD64 ; vérifier également les outils requis par les commandes sur la distribution cible. Les essais d'anciens candidats GNU/glibc ne qualifient pas ce nouvel artefact. Créer un compte de service dédié et un dossier persistant possédé par ce compte (mode 0700). Ses droits OS définissent les commandes possibles ; ne pas donner root pour la simple recette.
    4. Depuis ce compte, tester DNS/TCP/certificat puis lancer :
    python3 enroll-agent.py --binary /opt/appcontrol/appcontrol-agent \
  --gateway wss://gateway-appcontrol.apps.cluster.banque \
  --ca /etc/appcontrol/agent-ca.crt --token-file /chemin/prive/token \
  --state-dir /chemin/prive/agent --preflight-only
# Relancer sans --preflight-only pour enrôler puis exécuter l'agent.

    Le script n'expose pas le jeton dans les arguments du processus et vérifie le certificat. Le précontrôle ne consomme pas le jeton ; il ne prouve pas encore son autorisation. Après enrôlement, l'agent enregistre ses certificats et agent.yaml.

    1. Vérifier dans Agents qu'il est connecté via la gateway, puis l'affecter à une map avec des commandes de test. Le démarrage de cette map doit produire un état RUNNING et une trace d'action.
    2. Après succès, retirer le fichier de jeton et exécuter le service permanent directement : /opt/appcontrol/appcontrol-agent --config /chemin/prive/agent/agent.yaml. Configurer systemd avec le même compte, APP_ENV=production et un redémarrage sur échec. Le modèle scripts/qualification/appcontrol-agent.service.example fournit ces réglages, dont KillMode=process ; adapter ses chemins et son compte. NoNewPrivileges=true interdit une élévation via sudo/setuid : conserver les commandes dans les droits du compte de service. Ne pas supprimer le dossier de certificats à chaque redémarrage.

    Ne pas tuer tous les processus enfants à l'arrêt de l'agent : les applications lancées doivent survivre à son redémarrage. Qualifier les règles systemd et les droits des commandes avec l'équipe d'exploitation avant le POC.

    Pourquoi pas FROM scratch ?¶

    La release Linux est construite avec MUSL, mais le binaire seul n'est pas tout le service : confiance TLS et migrations restent nécessaires. L'agent exécute un shell et les outils des procédures. L'interface utilise nginx et PostgreSQL reste un service distinct. Le kit utilise les images minimales qualifiées par la release ; une base vide ne remplace pas automatiquement ce contrat.

    Preuves du parcours¶

    Les preuves applicables à une livraison sont celles de son kit : VALIDATION.fr.md, provenance.json, evidence/openshift/functional.json et les scans/SBOM. Elles identifient les sources et images réellement testées. Les rapports datés dans le dépôt conservent les essais historiques, notamment le parcours navigateur, l'agent extérieur et le transfert OCI des candidats. Ils ne remplacent pas les tests des nouveaux artefacts ni ceux du réseau client.
