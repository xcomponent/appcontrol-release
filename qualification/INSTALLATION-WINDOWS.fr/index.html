    Installer, mettre à jour et retirer AppControl sur OpenShift avec PowerShell et oc¶

    Le parcours Windows recommandé : la commande oc déjà installée, un petit paquet de fichiers PowerShell et YAML, puis une seule commande de déploiement.

    OpenShift télécharge lui-même les images depuis le registre autorisé. Le paquet léger ne contient aucune image ni aucun exécutable. Il n’installe pas oc et ne modifie pas le PATH du poste. Aucun Helm, Docker, Python, WSL, OpenSSL ou outil de transfert d’images n’est nécessaire sur le poste client.

    Produit : AppControl 1.24.1. Paquet : Windows léger 1.24.1-1.

    AppControl est le module d’exploitation de X4B — XComponent for Business, édité par INVIVOO. La version 1.24.1 ajoute l’accueil X4B, les comptes et accès, le badge de supervision et le raccordement des applications. Le module de génération rapproche les composants du catalogue complet. Le kit conserve le choix de l’URL publique, du compte administrateur et du projet, ainsi que le secret de téléchargement des images.

    La version 1.21.1 ajoute le contrat de génération pour l'IA du client, la publication de maps réparties sur plusieurs sites et l'attribution d'applications aux équipes. Le choix mock dans le prompt produit une map ordinaire, importée sur les agents choisis sans préparation de simulation obligatoire. Le kit conserve l'installation, la mise à jour et le retrait ciblés, la protection des fichiers locaux et les dépôts Artifactory séparés.

    La révision 1.21.1-2 du kit corrige le parcours de nettoyage/réinstallation et les chemins de miroir Artifactory. Elle utilise les mêmes images du produit 1.21.1. Les messages et confirmations des scripts sont désormais en anglais ; les noms de paramètres français des commandes existantes restent acceptés.

    Le kit 1.21.1-3 est un correctif PowerShell ciblé pour les anciens clients oc. Les images sont inchangées. Les preuves PUBLICATION-EVALUATION-1.21.1-2.json et QUALIFICATION-EVALUATION-1.21.1-2.zip concernent le précédent ZIP uniquement ; elles ne constituent pas une qualification complète de ce nouveau ZIP. Voir CORRECTIF-WINDOWS-1.21.1-3.fr.md joint à la release pour les vérifications ciblées.

    1. Ce qui sera déployé¶

    Le script vous demande quel projet/namespace utiliser, puis quel mode PostgreSQL installer. Les deux options utilisent les mêmes images AppControl et les mêmes scripts PowerShell.

    Choix au lancement PostgreSQL intégré PostgreSQL externe
    Usage Essai rapide dans un projet dédié Base dédiée fournie et gérée par la banque
    Base à préparer Aucune : identifiants et connexion générés Base dédiée et compte applicatif préparés par l'administrateur PostgreSQL ; seule la connexion applicative est fournie au script
    Dans OpenShift Un pod PostgreSQL et un volume persistant de 2 Gio Aucun pod, Service, volume ni image PostgreSQL déployé par l’installateur
    Services AppControl Interface web, backend, gateway Interface web, backend, gateway
    Démonstration Agent et map synthétique inclus Agent et map synthétique inclus
    Nombre de pods AppControl avec démonstration 5 4, la base externe est gérée séparément
    Recette Redémarre aussi le PostgreSQL de cette installation Ne redémarre jamais la base externe

    L’interface présente les applications et les maps, le backend gère les droits et les opérations, la gateway relie les agents, et l’agent exécute les commandes fictives de la démonstration. PostgreSQL conserve les données AppControl.

    Une seule des deux bases est utilisée. Le script ne bascule pas une installation existante d’un mode à l’autre : une migration des données se prépare séparément. Aucun Redis, fournisseur IA ou serveur MCP n’est requis pour cette installation.

    2. Les prérequis à obtenir une fois¶

    À préparer Ce qu’il faut concrètement
    Poste Windows Windows PowerShell 5.1, .NET Framework 4.8 et le oc déjà installé et approuvé par la banque. Scripts autorisés en mode PowerShell FullLanguage.
    Connexion Une connexion oc fonctionnelle au cluster du client, selon sa procédure habituelle.
    Projet / namespace Un projet existant fourni par la banque, de préférence dédié, avec les droits de déploiement. Il sera sélectionné dans le script ou fourni avec -Projet / -Namespace. Il n’est pas nécessaire d’avoir le droit de créer ou supprimer un projet.
    Stockage Uniquement pour PostgreSQL intégré : StorageClass utilisable et volume ReadWriteOnce de 2 Gio. En mode externe, aucun volume PostgreSQL n’est demandé.
    Quotas Nœuds Linux AMD64. Avec la démonstration : 1,15 vCPU et 992 Mio réservés en mode intégré ; 0,90 vCPU et 736 Mio côté AppControl en mode externe, hors base bancaire. Accepter aussi les limites des YAML et une marge pour les redémarrages.
    Registre Images accessibles par les nœuds, via Artifactory ou GHCR ; secret de lecture dans le projet si nécessaire. Cinq images avec PostgreSQL intégré ; quatre avec la base externe et la démonstration.
    Réseau et certificats Poste → API OpenShift et Route web HTTPS ; nœuds → registre ; échanges internes des services ; agent → Route gateway WSS 443. Les certificats des endpoints doivent être approuvés.
    Tunnel d’installation oc port-forward autorisé vers le projet : droit create sur pods/portforward et passage du tunnel par les éventuels proxies réseau. Pas de port entrant supplémentaire sur Windows.

    Le script ne crée pas le projet ni les accès au registre. Il ne requiert pas de compte administrateur Windows, de droit cluster-admin ni de SCC anyuid. Un projet dédié sépare les objets et les données ; il ne réserve pas à lui seul des nœuds physiques.

    Pour déployer une deuxième instance dans le même cluster, voir Installer une deuxième instance.

    Pour livrer une instance directement configurée, ajoutez -Configuration .\configuration.json à votre commande d’installation. Le socle AppControl, les gateways, les agents et la configuration applicative sont traités dans cette invocation. Contenu du JSON et commande complète

    3. Où sont les images et comment passe-t-on par Artifactory ?¶

    Le dépôt public de livraison XComponent fournit les scripts, les YAML et les rapports. Le canal public d’évaluation utilise cinq packages dédiés dans GitHub Container Registry, GHCR :

    ghcr.io/xcomponent/appcontrol-eval-backend
ghcr.io/xcomponent/appcontrol-eval-frontend
ghcr.io/xcomponent/appcontrol-eval-gateway
ghcr.io/xcomponent/appcontrol-eval-postgresql
ghcr.io/xcomponent/appcontrol-eval-agent

    PostgreSQL est également publié sur GHCR : package public appcontrol-eval-postgresql. Les images se trouvent dans la rubrique Packages, tandis que les scripts et les rapports se trouvent dans Releases. Le kit utilise cette image PostgreSQL XComponent préparée pour OpenShift ; une image postgres standard ou une image bancaire différente ne la remplace pas automatiquement.

    Ces images d’évaluation sont destinées au téléchargement anonyme : aucun compte GitHub, mot de passe ou jeton GHCR à fournir sur le poste client, dans OpenShift ou dans la connexion amont d’Artifactory. Les packages historiques appcontrol-backend, appcontrol-frontend, etc. restent privés : le nouveau parcours emploie bien les noms appcontrol-eval-*. Le dépôt de code source n’est pas rendu public par cette distribution.

    Le fichier images.lock.json du kit fixe les références et leurs empreintes SHA-256. Le script utilise ces empreintes, pas un tag latest susceptible de changer. Les versions suivantes du POC empruntent le même canal : la chaîne XComponent publie les images validées avec un nouveau numéro de version et produit le kit correspondant. Les copies conservent les digests ; elles ne nécessitent pas une deuxième compilation ni une manipulation chez le client.

    Cas A — le cluster peut télécharger directement depuis GHCR¶

    Lancer le script avec ses références par défaut. Omettre -Registre et -SecretImages. Les nœuds OpenShift doivent pouvoir joindre GHCR et faire confiance à ses certificats. C’est le cluster qui télécharge les images, pas le poste Windows.

    Cas B — la banque impose Artifactory¶

    flowchart LR
  O["OpenShift"] -->|"lecture selon les droits de la banque"| A["Artifactory de la banque"]
  A -->|"téléchargement anonyme des images d’évaluation"| G["GHCR XComponent : appcontrol-eval-*"]

    L’équipe plateforme prépare un dépôt Docker distant vers GHCR, éventuellement exposé par un dépôt virtuel. Elle autorise les cinq noms appcontrol-eval-* et fournit l’adresse Docker de lecture indiquée par « Set Me Up ». Ce n’est pas l’adresse de l’interface web Artifactory. Si les anciens noms privés étaient seuls autorisés, demander l’ajout des nouveaux noms avant le créneau.

    Qui prépare À faire une fois Ce que vous récupérez pour installer
    Équipe Artifactory Autoriser les packages publics appcontrol-eval-* et leur téléchargement par digest ; aucun compte GitHub amont nécessaire Le préfixe Docker des images d’évaluation
    Équipe OpenShift/Artifactory Autoriser les nœuds à lire dans le registre interne Si nécessaire, le nom d’un secret de lecture déjà créé dans votre projet
    Vous, avec les droits de déploiement du projet Lancer le script avec ces valeurs L’URL AppControl et la démonstration

    Les deux paramètres à ne pas confondre :

    • -Registre = adresse Docker du miroir et chemin du dépôt Artifactory, sans https://. Le script conserve le namespace source xcomponent : avec artifactory.intra.example/docker-ghcr, il produit artifactory.intra.example/docker-ghcr/xcomponent/appcontrol-eval-backend@sha256:…. Le préfixe complet artifactory.intra.example/docker-ghcr/xcomponent est également accepté, sans doubler xcomponent.
    • -SecretImages = nom d’un Secret OpenShift existant dans le projet cible, contenant les identifiants de lecture Artifactory. Si la plateforme l’a nommé artifactory-pull, utiliser -SecretImages 'artifactory-pull'. Ce n’est ni le mot de passe, ni le jeton, ni un fichier à fournir sur Windows.

    Les valeurs registry.banque.example/ghcr/xcomponent et lecture-artifactory utilisées dans les exemples sont fictives. Le script ne crée pas ce secret. Si l’accès Artifactory est déjà assuré par la plateforme ou si la lecture est anonyme, omettre -SecretImages après confirmation de l’équipe plateforme. L’accès amont public à GHCR ne rend pas automatiquement Artifactory public.

    Où saisir le token Artifactory ? Dans la console OpenShift, sélectionner le projet cible, puis Workloads → Secrets → Create → Image pull secret. Choisir par exemple le nom lecture-artifactory, renseigner le serveur du registre Docker, l’identifiant Artifactory associé au token, puis le token dans le champ Password. Utiliser ensuite -SecretImages 'lecture-artifactory'. Le secret est de type kubernetes.io/dockerconfigjson ; le type historique kubernetes.io/dockercfg est également accepté. Le script référence ce secret pour les pods qu’il déploie afin qu’OpenShift puisse tirer les images. Il ne faut mettre ni le token ni le nom de ce secret dans images.lock.json.

    Lors d’une reprise avec -SansDemo ou d’une mise à jour, l’agent de démonstration déjà présent conserve son pod et ses anciennes références de secret. Le script signale une différence éventuelle sans redémarrer cet agent : son identité se trouve dans un volume temporaire. Une nouvelle recette de démonstration utilise le nouveau secret, mais crée une nouvelle identité d’agent et une nouvelle map synthétique. Les services AppControl utilisent le secret fourni à la reprise.

    Exemples de résolution avec le kit 1.21.1-3 :

    Valeur de -Registre Préfixe obtenu avant appcontrol-eval-*
    artifactory.intra.example artifactory.intra.example/xcomponent
    artifactory.intra.example/docker-ghcr artifactory.intra.example/docker-ghcr/xcomponent
    artifactory.intra.example/docker-ghcr/xcomponent artifactory.intra.example/docker-ghcr/xcomponent

    Le script ne devine pas le nom du dépôt Artifactory : si l’adresse de lecture comporte docker-ghcr, ce chemin doit être fourni. Les noms d’images et leurs empreintes restent ceux du kit. Les préfixes déjà enregistrés par un ancien kit sont repris tels quels ; leur contenu n’est pas modifié silencieusement.

    Si la plateforme a volontairement aplati le chemin et expose par exemple artifactory.intra.example/flat/appcontrol-eval-backend, demander le traitement exact du préfixe, sans ajout de namespace :

    .\Deployer-AppControl.ps1 -Projet 'projet-fourni' `
  -Registre 'artifactory.intra.example/flat' -CheminRegistreExact `
  -SecretImages 'lecture-artifactory'

    L’alias anglais de cette option est -ExactRegistryPrefix. Une correction du chemin de registre ou du nom du secret de lecture peut être appliquée par une relance normale si le produit, les noms et les empreintes d’images sont inchangés. Un changement réel de version ou de contenu exige toujours -MettreAJour et une sauvegarde préalable.

    Une seule demande de préparation suffit : projet cible, préfixe exact des images appcontrol-eval-* dans Artifactory (et celui de PostgreSQL s’il est différent), nom éventuel du secret de lecture, et confirmation que les nœuds peuvent tirer ces images par digest. Les mêmes paramètres sont réutilisés pour les versions suivantes. La banque peut garder une étape d’approbation et de scan pour chaque nouvelle version.

    Le cache Artifactory se remplit à la demande. La plateforme peut aussi précharger les images ou utiliser un miroir interne, en conservant leurs digests. Il n’y a aucun Docker, transfert d’images ou accès d’administration Artifactory à installer sur le poste Windows.

    Références : accès anonyme aux images publiques GHCR, dépôts Docker JFrog, cache distant JFrog.

    Cas C — deux dépôts Artifactory distincts¶

    Si les quatre images AppControl et l’image PostgreSQL XComponent sont exposées par deux dépôts différents, fournir les deux préfixes Docker :

    .\Deployer-AppControl.ps1 -Projet appcontrol-evaluation -ModePostgreSQL Integre `
  -Registre 'artifactory.banque.example/appcontrol' `
  -RegistrePostgreSQL 'artifactory.banque.example/bases' `
  -SecretImages 'lecture-artifactory'

    Ces adresses sont des exemples à remplacer par les chemins fournis par la plateforme, sans https:// ni nom d’image. Le script construira notamment :

    artifactory.banque.example/appcontrol/xcomponent/appcontrol-eval-backend@sha256:…
artifactory.banque.example/bases/xcomponent/appcontrol-eval-postgresql@sha256:…

    -RegistrePostgreSQL ne change que le chemin d’accès de PostgreSQL. Il conserve le nom appcontrol-eval-postgresql et l’empreinte de l’image qualifiée. Les autres images utilisent -Registre. Ne pas modifier images.lock.json. Sans ce paramètre, PostgreSQL utilise le même préfixe que les autres images. Le namespace xcomponent est conservé dans les deux chemins. Pour un dépôt PostgreSQL aplati, utiliser -CheminRegistrePostgreSQLExact (-ExactPostgreSQLRegistryPrefix en anglais).

    Le secret éventuel doit permettre la lecture des deux dépôts. Si la plateforme assure déjà cet accès, omettre -SecretImages. Les deux préfixes sont enregistrés pour les relances. Pour les modifier après installation, préciser le préfixe à corriger lors d’une relance. Si seules les adresses changent et que les noms/digests des images restent identiques, aucune mise à jour de version n’est nécessaire. Un changement de produit ou d’image utilise le parcours -MettreAJour, après sauvegarde.

    Cette option concerne uniquement PostgreSQL intégré. Elle est refusée en mode externe, qui ne déploie aucune image de base. Si le second dépôt contient une image PostgreSQL standard ou propre à la banque, faire qualifier sa compatibilité séparément, ou utiliser une base déjà exploitée par la banque avec -ModePostgreSQL Externe et sa chaîne de connexion.

    4. Télécharger les petits fichiers de déploiement¶

    • Paquet Windows léger 1.24.1-1 — scripts et YAML
    • Empreinte SHA-256

    Le ZIP est uniquement un moyen pratique de transporter les fichiers texte. Après téléchargement ou transfert approuvé, vérifier l’archive dans PowerShell :

    $archive = 'appcontrol-openshift-windows-light-1.24.1-1.zip'
$attendu = ((Get-Content "$archive.sha256" -Raw).Trim() -split '\s+')[0]
if ((Get-FileHash $archive -Algorithm SHA256).Hash -ne $attendu) {
    throw 'Checksum mismatch: do not use this archive.'
}

    Utiliser Extraire tout dans l’Explorateur. Ouvrir le dossier contenant Deployer-AppControl.ps1, taper powershell dans la barre d’adresse, puis Entrée. Le dossier manifests contient le YAML OpenShift consultable avant installation. Les autres fichiers PowerShell sont les fonctions utilisées par le script ; ce ne sont pas des logiciels supplémentaires à installer.

    5. Lancer et choisir le projet et PostgreSQL¶

    Vérifier la connexion habituelle :

    oc whoami

    Le projet doit déjà exister. Si sa création vous est autorisée, vous pouvez d’abord utiliser oc new-project appcontrol-evaluation selon la procédure de la plateforme.

    Avec un accès direct à GHCR autorisé, lancer simplement :

    .\Deployer-AppControl.ps1

    Avec Artifactory, renseigner seulement l’adresse Docker et le secret de lecture fournis par la plateforme, puis laisser le script guider les choix :

    .\Deployer-AppControl.ps1 `
  -Registre 'registry.banque.example/ghcr/xcomponent' `
  -SecretImages 'lecture-artifactory'

    Ces deux valeurs sont des exemples à remplacer. Si la plateforme confirme que l’accès au registre interne est déjà assuré, omettre -SecretImages. Le canal public GHCR par défaut ne demande aucun secret GitHub.

    Le script présente successivement :

    1. Le serveur OpenShift de votre connexion et les projets accessibles. Saisir un numéro ou le nom du projet cible. Si la liste n’est pas autorisée, saisir le nom fourni par la plateforme.
    2. Le choix 1 — PostgreSQL intégré ou 2 — PostgreSQL externe.
    3. Pour une base externe, le choix TLS : 1 — vérifier le certificat (défaut) ou 2 — ignorer sa validation, puis les informations de connexion. Le chiffrement reste obligatoire dans les deux cas.
    4. Un récapitulatif du serveur, du contexte, du projet/namespace cible, du registre et du mode de base. Taper INSTALL pour autoriser le déploiement dans ce projet.

    Le namespace n’est jamais déduit silencieusement du projet courant. Le script utilise -n pour cibler les objets et une copie privée de la connexion ; il ne change pas le projet par défaut de votre configuration oc. Il ne crée pas implicitement de projet et refuse les conflits avec une installation existante.

    Installer une deuxième instance¶

    -Nom (alias -Name) définit le préfixe des ressources. La valeur par défaut est appcontrol-evaluation. Pour préparer une démo à côté de cette instance, utilisez par exemple appcontrol-demo. Le contrôle de conflit réserve aussi le préfixe suivi d’un tiret. Évitez donc appcontrol-evaluation-demo dans le même projet, car ce nom gênerait les opérations de maintenance de la première instance. Utilisez des minuscules, des chiffres et des tirets, avec un maximum de 40 caractères. La longueur du nom de projet et du nom d’installation additionnés doit rester inférieure ou égale à 54 pour les noms de Routes.

    $installation = @{
    Projet = 'projet-client'
    Nom = 'appcontrol-demo'
    ModePostgreSQL = 'Integre'
}
.\Deployer-AppControl.ps1 @installation -Verifier
.\Deployer-AppControl.ps1 @installation

    Remplacez projet-client par le projet prévu pour la démo. Si le client utilise Artifactory, ajoutez au tableau les valeurs Registre et, si nécessaire, SecretImages fournies pour ce projet. La première commande vérifie la connexion, les droits et les conflits. La seconde déploie l’instance après confirmation.

    Le nom apparaît notamment dans appcontrol-demo-backend, data-appcontrol-demo-postgresql-0 et, avec les Routes par défaut, https://appcontrol-demo-projet-client.<domaine-apps>. Le dossier d’état local, les certificats, les identifiants et la base intégrée sont propres à l’instance. En PostgreSQL externe, fournissez une base dédiée à cette deuxième installation.

    Pour réserver la démo à votre équipe, demandez un projet dédié avec les droits correspondants et une Route dont l’accès est limité par la plateforme. Le projet contrôle les droits OpenShift sur les ressources, et la Route contrôle l’accès réseau au site. Le nom distingue les instances dans le projet. -UrlPublique et -UrlGateway permettent de spécifier des adresses approuvées par la plateforme. Utilisez des adresses distinctes pour les deux installations.

    Conservez le même projet et le même nom lors des relances et des mises à jour. Pour contrôler le périmètre du retrait avant toute suppression, lancez :

    .\Desinstaller-AppControl.ps1 -Namespace 'projet-client' -Name 'appcontrol-demo' -Preview

    Choix 1 : PostgreSQL intégré¶

    Aucune chaîne de connexion à fournir. Le script prépare la base, les identifiants, les certificats et le stockage. Pour prédéfinir ces deux choix :

    .\Deployer-AppControl.ps1 -Projet appcontrol-evaluation -ModePostgreSQL Integre `
  -Registre 'registry.banque.example/ghcr/xcomponent' `
  -SecretImages 'lecture-artifactory'

    Ajouter -ClasseStockage 'nom-fourni-par-la-plateforme' uniquement si la classe par défaut ne convient pas. Cette option concerne uniquement la base intégrée.

    Choix 2 : PostgreSQL externe fourni par la banque¶

    Avant le créneau, demander à l’équipe base de données et à la plateforme :

    • Une base dédiée et un compte applicatif préparés à l'avance par l'administrateur PostgreSQL. Le compte doit pouvoir créer et modifier les objets du schéma AppControl. Le script ne crée ni instance, ni base, ni comptes PostgreSQL sur le serveur bancaire. Ne pas utiliser une base métier existante.
    • La chaîne de connexion du seul compte applicatif au format URI, par exemple postgresql://utilisateur:mot-de-passe@postgres.banque.example:5432/appcontrol?sslmode=verify-full. Ce n’est pas une chaîne ADO.NET Host=...;Username=.... Les caractères réservés du nom d’utilisateur et du mot de passe doivent être encodés dans l’URI. Ne pas fournir les identifiants de l'administrateur PostgreSQL au script.
    • Pour le mode TLS par défaut, le certificat public de l’autorité de certification de PostgreSQL, au format PEM. Une autorité interne autosignée convient. Le nom DNS de l’URI doit correspondre au certificat du serveur. Le mode par défaut utilise verify-full. Le mode de compatibilité ci-dessous ne demande pas de fichier CA.
    • Les adresses ou plages CIDR approuvées de la base, par exemple 10.20.30.40/32, ainsi que son port. Elles limitent la sortie réseau du backend. Les ouvertures générales 0.0.0.0/0 et ::/0 sont refusées. Une règle réseau ou un pare-feu bancaire peut aussi nécessiter une autorisation par la plateforme.

    PostgreSQL 16 est la version de référence de cette livraison. Il y a deux rôles distincts dans la préparation : l'administrateur de la base crée les objets d'accueil, puis AppControl se connecte avec le compte applicatif. L'installateur ne gère pas deux comptes automatiquement et ne reçoit qu'une chaîne de connexion.

    Le même compte applicatif sert au fonctionnement et aux migrations exécutées par le backend au démarrage, y compris lors des mises à jour. Il lui faut des droits DDL pour créer et modifier les objets du schéma ; de simples droits lecture/écriture ne suffisent pas. Le profil de référence utilise le compte applicatif propriétaire de sa base dédiée, sans SUPERUSER, CREATEDB ni CREATEROLE. L'administrateur PostgreSQL doit valider les droits équivalents si la banque impose une autre organisation des rôles ou des schémas.

    Lancer le script avec le mode externe ; il demandera les informations manquantes :

    .\Deployer-AppControl.ps1 -Projet appcontrol-evaluation -ModePostgreSQL Externe `
  -Registre 'registry.banque.example/ghcr/xcomponent' `
  -SecretImages 'lecture-artifactory'

    La saisie de la chaîne de connexion est masquée. Elle n’apparaît ni dans l’historique PowerShell, ni dans les YAML livrés, ni dans le récapitulatif. Elle est conservée dans le dossier privé de reprise, puis transmise à un Secret OpenShift. Ce dossier contient des secrets lisibles par votre compte Windows et le système : ne pas le partager. Les administrateurs autorisés du cluster peuvent accéder aux Secrets selon les droits de la banque.

    On peut préparer les valeurs non secrètes avec -CertificatPostgreSQL 'C:\Certificats\ca-postgres.pem' et -CidrPostgreSQL @('10.20.30.40/32','10.20.30.41/32'). Pour une automatisation, -ChaineConnexion attend un objet SecureString, obtenu par exemple avec Read-Host -AsSecureString ; ne pas écrire un mot de passe en clair dans la commande. -NonInteractif exige le projet et le mode explicites à la première installation.

    Option : ignorer la validation du certificat PostgreSQL¶

    Disponible depuis le paquet léger 1.20.4-3. C’est l’équivalent d’une option HTTPS qui accepte un certificat non reconnu. Elle est désactivée par défaut et concerne uniquement la connexion du backend à PostgreSQL externe.

    Ajouter -IgnorerCertificatPostgreSQL dès la première installation :

    .\Deployer-AppControl.ps1 -Projet appcontrol-evaluation -ModePostgreSQL Externe `
  -Registre 'registry.banque.example/ghcr/xcomponent' `
  -SecretImages 'lecture-artifactory' `
  -IgnorerCertificatPostgreSQL

    Remplacer les deux valeurs de registre et de secret par celles de la plateforme. Sans option en ligne de commande, l’assistant interactif propose aussi ce choix lors d’une nouvelle installation externe si aucun fichier CA n’a été fourni. Entrée conserve le mode avec vérification.

    Dans ce mode :

    • La connexion reste chiffrée en TLS (sslmode=require). Un serveur PostgreSQL sans TLS est refusé ; il n’existe aucun repli en clair.
    • Le certificat et le nom du serveur ne sont plus vérifiés : un certificat serveur autosigné ou non reconnu ne bloque plus la connexion. L’identité du serveur n’est donc plus garantie par TLS.
    • Aucun fichier CA n’est demandé ni monté. Ne pas fournir -CertificatPostgreSQL en même temps ; le script refuse ce mélange.
    • Les identifiants PostgreSQL, les droits sur la base et les restrictions réseau restent nécessaires. L’option ne contourne pas une erreur de mot de passe, de pare-feu ou d’accès aux images.
    • Les certificats de l’API OpenShift, d’Artifactory/GHCR, de l’interface et des échanges gateway/agents restent vérifiés selon leur configuration habituelle.

    Le script affiche ce choix avant déploiement et dans les rapports. La chaîne saisie peut omettre sslmode : l’assistant impose le mode choisi. Saisir simplement sslmode=require dans une URI sans choisir l’option ne désactive pas la vérification. disable, allow, prefer et verify-ca ne sont pas acceptés dans ce parcours.

    Le choix est enregistré pour la reprise ; la commande de reprise affichée rappelle l’option lorsqu’elle est active. Comme pour la base et la CA, une installation existante ne change pas implicitement de politique TLS : un choix différent est refusé et demande une procédure de modification préparée. Les dossiers issus du paquet 1.20.4-2 restent interprétés comme verify-full.

    Une fois connecté, AppControl gère son schéma et ses données. Il ne déploie pas d’image PostgreSQL, ne crée aucun volume de base et ne redémarre pas le serveur externe. La sauvegarde, l’exploitation et la disponibilité de cette base restent gérées selon la procédure de la banque.

    Ce que fait le déploiement¶

    Le script vérifie les droits OpenShift et les fichiers, prépare les secrets et les certificats, traite le Template YAML avec oc process, puis applique les objets avec oc apply. Le profil externe retire les objets PostgreSQL et adapte la sortie réseau du backend avant application. Les nœuds OpenShift téléchargent les seules images nécessaires depuis le registre autorisé. La validation préalable de l'URI ne teste pas la connexion PostgreSQL ni les droits DDL : ceux-ci sont exercés au démarrage du backend et lors de ses migrations.

    Le script attend ensuite les services, enregistre la gateway, puis crée l’agent et la map synthétique. La recette redémarre les services AppControl pour vérifier la reconnexion et la conservation des données. PostgreSQL est redémarré uniquement en mode intégré, dans le projet d’évaluation. Ajouter -SansDemo pour installer les services seuls : quatre pods en mode intégré, trois en mode externe.

    6. Ouvrir et tester AppControl¶

    Le script affiche l’URL de l’interface et le chemin privé des identifiants administrateur. Le dossier d’état se trouve par défaut sous %LOCALAPPDATA%\AppControl\Installations, avec des droits limités à l’utilisateur Windows et au système. Ne pas envoyer ce dossier avec un rapport.

    Dans le navigateur, ouvrir l’application Qualification dependencies… indiquée par la recette. Elle comporte deux composants synthétiques :

    Action Ce que l’on constate
    Start All database-probe démarre, puis api-probe ; les deux passent au vert.
    Stop All L’API s’arrête d’abord, puis sa dépendance.
    Historique Les commandes exécutées et leurs résultats sont visibles.

    Les commandes sont des touch, test -f et rm sur des marqueurs dans /tmp du pod agent. Le démarrage de api-probe vérifie le marqueur de database-probe. Ce ne sont ni la vraie base PostgreSQL d’AppControl ni des services de la banque. Aucune commande métier n’est exécutée sur le poste Windows.

    Les pods AppControl et la map restent disponibles après fermeture de PowerShell. L’agent de qualification est temporaire : son identité est conservée tant que son pod existe. Après remplacement de ce pod, relancer la recette crée un nouvel agent et une nouvelle map ; utiliser la nouvelle map indiquée. Un agent durable doit conserver son dossier d’identité sur un stockage persistant.

    Mettre à jour le POC¶

    La première installation et les versions suivantes utilisent le même script PowerShell. Chaque livraison apporte un nouveau kit et son images.lock.json ; il n’y a ni image à transporter sur le poste, ni compte GitHub à créer.

    1. Télécharger le nouveau kit depuis les releases XComponent, vérifier son empreinte et l’extraire dans un nouveau dossier. Conserver le dossier privé de l’installation existante.
    2. Faire approuver les nouvelles images dans le registre bancaire si sa politique l’exige.
    3. Sauvegarder PostgreSQL avant la mise à jour et disposer d’une procédure de restauration. Pour une base externe, obtenir la confirmation de l’équipe base de données. Pour la base intégrée, appliquer la procédure de sauvegarde retenue pour le POC. Le script ne crée pas cette sauvegarde et un PVC n’en tient pas lieu.
    4. Réserver une interruption des services AppControl, puis lancer depuis le nouveau kit :
    .\Deployer-AppControl.ps1 -Projet appcontrol-evaluation -MettreAJour

    Si l’interface ou le backend de l’installation actuelle a été supprimé à la main, restaurer d’abord les services avec le kit de la version déjà installée et le dossier privé d’origine :

    .\Deployer-AppControl.ps1 -Projet 'projet-fourni' -Nom 'appcontrol-evaluation' `
  -DossierEtat 'C:\AppControl\Etat' -SansDemo

    Remplacer ces valeurs par celles de l’installation. Cette reprise conserve la base et les maps ; elle n’exécute pas une nouvelle démonstration. Une fois l’interface accessible, lancer -MettreAJour depuis le nouveau kit cible. La mise à jour doit pouvoir relever l’inventaire des applications avant de les modifier. Si cet inventaire est inaccessible, elle affiche cette commande de réparation sans créer un nouveau journal de mise à jour bloquant. Si une vraie mise à jour était déjà en cours, conserver son kit cible et sa sauvegarde ; ne pas déployer une ancienne version sur une base potentiellement migrée.

    Reprendre le même -Nom si l’installation initiale utilisait un nom personnalisé, et le même -DossierEtat si vous aviez choisi un autre emplacement. Le script retrouve les paramètres enregistrés : registre AppControl, éventuel registre PostgreSQL distinct, éventuel secret d’images, mode PostgreSQL, connexion et politique TLS. L’assistant demande confirmation que la sauvegarde a été réalisée avant d’appliquer la mise à jour.

    Pour passer d’une ancienne installation utilisant directement le miroir privé à la distribution publique XComponent, préciser le nouveau registre :

    .\Deployer-AppControl.ps1 -Projet appcontrol-evaluation `
  -MettreAJour -Registre 'ghcr.io/xcomponent'

    Avec Artifactory, conserver le préfixe interne approuvé et faire autoriser les nouveaux noms appcontrol-eval-*. Un ancien secret de lecture est conservé : l’agent déjà installé peut encore utiliser son image privée. Le passage au canal public ne révoque pas automatiquement ces accès existants.

    Pour un lancement non interactif, après avoir réellement effectué la sauvegarde :

    .\Deployer-AppControl.ps1 -Projet appcontrol-evaluation `
  -MettreAJour -SauvegardeConfirmee -NonInteractif

    -SauvegardeConfirmee est une attestation de l’opérateur, pas une commande de sauvegarde. L’installation garde son projet, son stockage, ses identifiants et ses certificats. Le backend applique les migrations de sa version au démarrage. Changer de base, de mode PostgreSQL ou de politique TLS reste une opération séparée, refusée implicitement par ce parcours.

    La mise à jour concerne les services de contrôle backend, interface web et gateway, ainsi que l’image PostgreSQL lorsque la base est intégrée. Elle ne rejoue pas la démonstration : les maps et l’agent existants sont conservés. Elle vérifie les identifiants des applications et agents, une empreinte de la configuration des maps (commandes, dépendances et paramètres), ainsi que la reconnexion des agents qui étaient connectés avant l’opération.

    Les agents existants, dans le cluster ou sur des machines externes, ne sont ni réenrôlés, ni redémarrés, ni mis à jour automatiquement par ce parcours. Leur version reste inchangée. Une mise à jour d’agent se prépare séparément, avec conservation de son identité et vérification de sa compatibilité avec la nouvelle version des services. L’image agent du nouveau kit sert aux nouvelles démonstrations ; elle ne remplace pas silencieusement un agent en cours.

    Le changement des images exige -MettreAJour ; une simple reprise ne le déclenche jamais. Le script ne met pas automatiquement le POC sur la dernière version publiée : vous choisissez et validez le kit à déployer. Il ne réalise pas de retour arrière automatique de PostgreSQL après une migration.

    Le journal privé update.json distingue une mise à jour complète d’une opération incomplète. En cas d’échec, les anciennes références restent conservées pour le diagnostic ; cela ne signifie pas que les anciens pods ou l’ancienne base ont été restaurés. Le script bloque la reprise normale et demande de relancer le même kit cible avec -MettreAJour pour terminer. Garder le dossier privé et la sauvegarde PostgreSQL ; ne pas modifier les verrous à la main.

    Retirer AppControl sans supprimer le projet¶

    Le nettoyage cible l’installation choisie. Il ne supprime jamais le projet/namespace ni une base PostgreSQL externe. Il convient donc à un projet fourni par la banque, sans droit de création ou de suppression de projet.

    Depuis le kit 1.21.1-3, commencer par le récapitulatif sans modification :

    .\Desinstaller-AppControl.ps1 -Namespace 'projet-fourni' -Name 'appcontrol-evaluation' -Preview

    Puis retirer les services en conservant les données et la configuration :

    .\Desinstaller-AppControl.ps1 -Namespace 'projet-fourni' -Name 'appcontrol-evaluation'

    Remplacer le projet et le nom par les valeurs de l’installation initiale. Si vous aviez choisi un autre dossier privé, ajouter -StateDirectory 'C:\AppControl\Etat' avec son chemin réel. Les paramètres français restent acceptés : -Projet, -Nom, -Verifier et -DossierEtat sont équivalents aux alias utilisés ici.

    Les messages et confirmations sont en anglais. Le récapitulatif indique la cible, les objets à retirer et ceux à conserver ; l’invite de confirmation indique explicitement le texte à saisir. -Preview ne supprime rien et ne modifie pas les fichiers locaux.

    Par exemple, pour -Name appcontrol-evaluation, l’invite affiche :

    To remove the listed resources from project projet-fourni, type the installation name appcontrol-evaluation

    Saisir appcontrol-evaluation, puis Entrée. Si vous aviez choisi un autre nom, saisir ce nom exact affiché dans l’invite.

    Un nettoyage qui peut être repris¶

    Un objet déjà supprimé à la main n’est pas une erreur. Le script traite les objets restants un par un et poursuit le nettoyage si un objet est inaccessible, a changé de propriétaire ou ne peut pas être supprimé. Il termine avec un bilan des objets supprimés, déjà absents, ignorés et en échec. Les objets ignorés ou en échec sont nommés pour permettre de corriger le problème, puis de relancer exactement la même commande. Un résultat incomplet n’est pas présenté comme une désinstallation réussie.

    Le changement de nom du contexte oc ne bloque plus à lui seul la reprise, si le serveur, le namespace et le nom de l’installation correspondent. Une connexion vers un autre cluster ou une ressource appartenant à une autre installation n’est pas acceptée comme cible de suppression.

    Sans -RemoveAll Résultat

    PostgreSQL intégré Pod retiré ; volume de données conservé
    Secrets et ConfigMaps AppControl Conservés pour garder identifiants, certificats et configuration
    Secret de lecture Artifactory Conservé
    PostgreSQL externe Base et données inchangées
    Projet et autres applications Inchangés

    Le script ne supprime pas les agents installés sur des machines externes ni une installation Helm. Pour un complément de simulation actif, retirer d’abord ce complément avec Configurer-Simulation.ps1 -DossierEtat <dossier-prive> -Supprimer, puis relancer la désinstallation. Le nettoyage conserve alors les services et la base nécessaires à cette opération ; il peut retirer des ressources indépendantes, comme l’agent de démonstration. Les éléments conservés sont identifiés dans le bilan.

    Pour remettre les services en conservant les données, relancer Deployer-AppControl.ps1 avec le même kit, le même projet, le même nom et le dossier privé conservé. Les objets manquants du déploiement sont recréés à partir de cette configuration. La base conserve les maps. L’agent de démonstration peut recevoir une nouvelle identité après remplacement de son pod ; ajouter -SansDemo (-SkipDemo) pour remettre seulement les services.

    Supprimer complètement les ressources de l’évaluation¶

    -RemoveAll peut détruire les données PostgreSQL intégrées. Réaliser une sauvegarde si elles doivent être conservées. Un PVC n’est pas une sauvegarde.

    .\Desinstaller-AppControl.ps1 -Namespace 'projet-fourni' -Name 'appcontrol-evaluation' `
  -RemoveAll -Preview

    Puis exécuter le même nettoyage sans -Preview :

    .\Desinstaller-AppControl.ps1 -Namespace 'projet-fourni' -Name 'appcontrol-evaluation' `
  -RemoveAll

    -RemoveAll est l’alias anglais de -SupprimerDonnees. Il ajoute les volumes, Secrets et ConfigMaps propres à l’installation. Les Secrets de téléchargement Artifactory sont toujours conservés, même avec -RemoveAll et -WithoutState. Ils peuvent être réutilisés pour la prochaine installation. Le projet, les autres applications et la base PostgreSQL externe restent inchangés.

    L’assistant affiche d’abord :

    This can permanently delete stored data and registry credentials. Type DELETE DATA to confirm your backup or accept their loss

    Saisir DELETE DATA, avec l’espace, puis Entrée. Saisir ensuite le nom exact de l’installation à la seconde invite. En mode non interactif, l’attestation doit être explicite :

    .\Desinstaller-AppControl.ps1 -Namespace 'projet-fourni' -Name 'appcontrol-evaluation' `
  -RemoveAll -BackupConfirmed -NonInteractive

    -BackupConfirmed ne réalise aucune sauvegarde. Le dossier privé Windows est conservé pour le diagnostic ; le nettoyage ne le détruit pas.

    Si le dossier privé a été perdu ou endommagé¶

    Utiliser le nettoyage sans état local en donnant explicitement le projet et le nom de l’installation :

    .\Desinstaller-AppControl.ps1 -Namespace 'projet-fourni' -Name 'appcontrol-evaluation' `
  -WithoutState -RemoveAll -Preview

    Après lecture du plan, retirer -Preview pour exécuter. -WithoutState (-SansEtat) identifie les ressources par les marqueurs de propriété AppControl et leurs noms attendus ; il n’adopte pas une ressource simplement parce que son nom commence de la même manière. Le dossier privé n’est pas modifié ; un journal de nettoyage séparé est écrit à côté. -ImagePullSecret 'lecture-artifactory' permet de désigner explicitement un secret à conserver ; il n'autorise jamais sa suppression.

    Réinstaller proprement après le nettoyage complet¶

    Il n’est pas nécessaire de supprimer le projet ni d’effacer manuellement le dossier privé. Après retrait des ressources de l’ancienne installation :

    .\Deployer-AppControl.ps1 -Projet 'projet-fourni' -Nom 'appcontrol-evaluation' `
  -Reinstaller

    -Reinstaller (-Reinstall) vérifie que les anciennes ressources AppControl, y compris leurs données et configuration conservées, ont été retirées. Un secret de lecture Artifactory protégé peut rester. Le script archive l’ancien état local et son journal de nettoyage, puis prépare de nouveaux identifiants. Il ne réutilise pas les certificats d’une base effacée. Si le bilan de suppression mentionne encore des ressources AppControl, terminer leur nettoyage avant cette commande. Reprendre le même -DossierEtat si son emplacement était personnalisé.

    Avec Artifactory, fournir à nouveau le registre et le secret de lecture à utiliser ; recréer ce secret s’il a été supprimé :

    .\Deployer-AppControl.ps1 -Projet 'projet-fourni' -Nom 'appcontrol-evaluation' `
  -Reinstaller -Registre 'artifactory.intra.example/docker-ghcr' `
  -SecretImages 'lecture-artifactory'

    Pour une base externe, faire préparer une base dédiée vide ou faire valider son nettoyage par l’administrateur PostgreSQL, puis confirmer explicitement :

    .\Deployer-AppControl.ps1 -Projet 'projet-fourni' -Nom 'appcontrol-evaluation' `
  -Reinstaller -ModePostgreSQL Externe -BaseExterneVideConfirmee

    -BaseExterneVideConfirmee (-EmptyExternalDatabaseConfirmed) est une attestation, pas une commande SQL : le script n’efface jamais la base bancaire. Pour conserver une base existante et ses maps, utiliser la reprise avec l’état d’origine, et non une réinstallation avec de nouvelles identités.

    Reprendre et diagnostiquer¶

    Reprendre la même version, hors mise à jour incomplète, ne nécessite pas -MettreAJour. Conserver le dossier privé, les mêmes produit, projet et nom et reprendre avec la commande indiquée par le script. Pour reprendre les services en conservant la démonstration existante, ajouter -SansDemo. Sans cette option, la recette peut créer une nouvelle démonstration.

    Le kit corrigé 1.21.1-3 peut remplacer le kit 1.21.1-1 sans changer les images du produit. Un préfixe Artifactory erroné ou un nouveau nom de secret de lecture peuvent être fournis à cette relance. Le contrôle porte sur les noms et empreintes des images, pas sur la seule adresse du miroir.

    Le script refuse d’écraser une installation Helm ou des objets qui ne lui appartiennent pas. Ne pas supprimer le dossier privé pour contourner un refus.

    Si une première installation a été bloquée par SeSecurityPrivilege, extraire le nouveau kit dans un autre dossier et y relancer la même commande, avec le même projet, le même nom et, si vous en aviez fourni un, le même -DossierEtat. Le correctif protège les fichiers locaux et reprend la préparation avec les paramètres conservés. Ne pas ajouter -MettreAJour pour débloquer cette première installation ; cette option sert à changer une installation déjà déployée. Ne pas supprimer son dossier d’état.

    Ressource existante refusée Vérifier le projet et le nom. Pour reprendre les données, conserver l’état d’origine ; pour repartir à vide, nettoyer avec -RemoveAll, puis utiliser -Reinstaller. Aucun écrasement d’une ressource étrangère.
    Nettoyage partiel ou objet déjà supprimé Relancer la même commande de désinstallation ; les absences sont acceptées et les autres objets sont traités. Lire le bilan des objets ignorés/en échec.
    Dossier privé perdu ou endommagé Afficher le plan avec -WithoutState -Namespace ... -Name ... -Preview, puis retirer -Preview si la cible est correcte.

    Configuration après installation : équipes et topologie¶

    Le chemin le plus court est de fournir le JSON à Deployer-AppControl.ps1. Le script installe le socle puis applique la configuration dans la même invocation. Copiez le configuration.example.json du kit en configuration.json et adaptez les codes, noms et comptes à votre projet.

    .\Deployer-AppControl.ps1 -Projet appcontrol-poc -Nom appcontrol-demo -ModePostgreSQL Integre `
  -Configuration .\configuration.json -Verifier
.\Deployer-AppControl.ps1 -Projet appcontrol-poc -Nom appcontrol-demo -ModePostgreSQL Integre `
  -Configuration .\configuration.json

    Ajoutez à ces commandes vos options habituelles de registre, de stockage, de base externe ou de route publique. -SansDemo installe le socle et applique votre JSON sans charger la démo bancaire intégrée. Sur une installation neuve, -Verifier valide le fichier et les prérequis accessibles. La recette des gateways, des agents et de l’API AppControl a lieu une fois le socle disponible.

    Champ JSON Ce que le déploiement configure
    hostings, sites Regroupements d’infrastructure, codes de site et nombre de gateways par site.
    agent_profile, agent_storage Profil et stockage de l’agent Linux persistant de chaque site.
    catalog Types de composants à ajouter au catalogue technique.
    users, teams Comptes locaux, rôles, équipes et rattachement des membres.
    permissions Droits des équipes sur les maps déjà présentes au moment de la configuration.
    document_source.secret_name Référence facultative au Secret OpenShift de la source documentaire X4B.
    embedded.allowed_origins, embedded.simulation_sites Origines HTTPS des portails et codes des sites dédiés à la simulation Embedded.

    Pour appliquer uniquement la configuration à une installation existante, utilisez le dossier d’état privé indiqué par l’installateur.

    .\Configurer-AppControl.ps1 -DossierEtat 'CHEMIN_DU_DOSSIER_PRIVE' -Configuration .\configuration.json

    Chaque entrée de sites crée un agent Linux persistant et le nombre de gateways indiqué dans gateways (1 par défaut, jusqu’à 8). Un hosting regroupe des sites. La gateway du socle est déployée séparément. Les gateways d’un site partagent un service interne auquel se connecte son agent. Les agents et gateways sont déployés dans le projet OpenShift de l’installation. Ajouter un site au fichier puis relancer complète la topologie. Un changement de nombre de gateways ou de stockage sur un site déjà configuré se traite séparément.

    agent_profile s’applique à tous les agents créés par ce fichier. standard, indiqué dans configuration.example.json, enregistre des agents ordinaires. mock-linux utilise le même agent et le désigne comme cible par défaut de l’assistant de simulation de son site. Le script historique de simulation retient mock-linux si le champ est omis. Indiquer la valeur explicitement dans le JSON.

    site_type classe le site, par exemple primary ou dr. Pour une map, le profil de rattachement définit quels agents exécutent ses composants. Un profil de reprise peut sélectionner d’autres agents. Le type du site et la présence de plusieurs gateways ne suffisent pas à configurer cette bascule. Affecter les agents aux composants

    Exemple de sections à ajouter au fichier (remplacer les valeurs fictives) :

    {
  "users": [{"email": "operateur@example.test", "name": "Operateur", "role": "operator"}],
  "teams": [{"name": "Exploitation", "members": ["operateur@example.test"]}],
  "permissions": [{"app": "Application existante", "team": "Exploitation", "level": "operate"}]
}

    Les mots de passe des nouveaux comptes locaux sont demandés en saisie masquée. En mode -NonInteractif, utilisez des comptes déjà créés ou laissez users vide. Les comptes existants et leurs mots de passe sont conservés. La configuration ajoute les membres manquants ; elle ne retire aucun membre ni aucun droit existant. Un rôle ou droit divergent bloque et doit être modifié explicitement dans AppControl. Les membres peuvent référencer des utilisateurs existants sans les redéclarer dans users.

    Les ressources déjà créées sont retrouvées lors d’une reprise. La configuration n’est pas une transaction globale : conserver le fichier et le dossier privé puis relancer après correction d’un échec. Aucun secret n’est affiché dans l’aperçu.

    Ajoutez un site SIM avec une gateway et déclarez son code sous embedded. Le kit crée le site, la gateway et l’agent, retrouve les UUID après l’enrôlement et configure le backend et le frontend. Une paire suffit pour les maps qui décrivent plusieurs sites. Réservez la paire à Embedded. Avec mock-linux, le kit réserve ces sites à Embedded et enregistre les autres comme cibles par défaut de l’import mock historique.

    {

  "agent_profile": "standard",
  "sites": [
    { "code": "VEGA", "name": "Vega", "site_type": "primary", "gateways": 1 },
    { "code": "SIRIUS", "name": "Sirius", "site_type": "primary", "gateways": 1 },

    Echeances des certificats et jetons¶

    Le jeton de gateway dure 30 jours et sert à chaque reconnexion au backend. Le jeton d’enrôlement initial d’un agent sert une fois. Après l’enrôlement, l’agent se reconnecte avec son certificat client, valable 365 jours par défaut. Les certificats des services et des gateways du kit durent 90 jours.

    Sur le poste Windows, connectez oc au cluster de l’installation, puis lancez le connecteur avec le dossier privé indiqué par l’installeur.

    .\Maintenir-AppControl.ps1 -DossierEtat 'CHEMIN_D_ETAT' -Watch

    Dans AppControl, ouvrez Certificates & tokens → Maintenance. Sélectionnez une brique, consultez l’échéance et confirmez Request renewal. Le connecteur doit rester ouvert pendant l’opération. Il utilise la connexion OpenShift du poste et le compte administrateur conservé dans le dossier privé. L’écran affiche la progression de la demande et le résultat. Les jetons et les clés privées restent dans le dossier d’état ou dans les Secrets OpenShift. Le compte OpenShift doit pouvoir mettre à jour les Secrets et redéployer les briques de cette installation. Le renouvellement d’un agent nécessite aussi l’accès pods/exec à son pod. Arrêtez le connecteur avant de mettre à jour, réinstaller ou désinstaller l’instance.

    Le parcours gère les jetons et certificats des gateways du socle et des sites, les certificats de transport émis par le kit et les certificats des agents persistants configurés par le kit. La reconnexion peut interrompre brièvement les contrôles. Les autorités de certification, la Route HTTPS fournie par la plateforme et les agents hors cluster demandent une intervention de leur gestionnaire. Pour ces derniers, suivre la procédure de réenrôlement avec le même nom d’agent. Si la Route hérite du certificat du routeur, son échéance peut ne pas être disponible dans l’inventaire.

    Si une rotation interrompue laisse un fichier de récupération, fermez le connecteur, vérifiez le projet ciblé et restaurez l’ancienne valeur depuis le poste connecté à OpenShift. Vérifiez ensuite la santé du service. Conservez le dossier privé tant que la restauration n’est pas terminée.

    .\Maintenir-AppControl.ps1 -DossierEtat 'CHEMIN_D_ETAT' -Restore

    Si plusieurs certificats de transport ont expiré et bloquent l’interface, renouvelez le transport depuis Windows tant que son autorité reste valide. Le script renouvelle les services dans l’ordre et vérifie ensuite l’API.

    .\Maintenir-AppControl.ps1 -DossierEtat 'CHEMIN_D_ETAT' -RecoverTransport

    Choisir le premier administrateur¶

    À la première installation interactive, Deployer-AppControl.ps1 demande l’email administrateur (Entrée conserve admin@example.test), puis un mot de passe masqué d’au moins 12 caractères et sa confirmation. Ce compte est créé comme administrateur par l’initialisation AppControl. Il n’existe pas de mot de passe commun livré dans le ZIP.

    Les identifiants sont conservés dans le fichier privé credentials.json du dossier d’état indiqué par l’installeur, sous %LOCALAPPDATA%\AppControl\Installations. Ce fichier est créé sur le poste pendant l’installation ; il n’est pas dans le kit téléchargé.

    Une reprise conserve le compte et le mot de passe existants. Fournir de nouveaux identifiants ne réinitialise pas un compte déjà créé. Le script Configurer-AppControl.ps1 réutilise ces identifiants pour configurer les sites, les agents, les utilisateurs et les équipes déclarés dans votre configuration.

    Pour automatiser, les paramètres -AdminEmail et -AdminPassword permettent de fournir l’email et un SecureString obtenu avec Read-Host -AsSecureString. Avec -NonInteractif et sans mot de passe fourni, un mot de passe aléatoire est généré et enregistré dans ce même fichier privé. Ne mettez pas de mot de passe en clair dans le fichier de configuration.

    Le kit 1.21.1-6 conserve les images 1.21.1. Ses tests ciblés de scripts ne remplacent pas une nouvelle qualification complète sur le cluster du client.

    Fournir explicitement l’URL publique (kit 1.21.1-7)¶

    Sans option supplémentaire, le domaine reste détecté automatiquement comme avant. À la première installation ou après un retrait volontaire complet, ajouter à votre commande habituelle :

    -UrlPublique 'https://appcontrol-evaluation-monprojet.pres.cluster.example'

    Le nom complet est utilisé tel quel : aucun nom de projet n’est ajouté. Utiliser HTTPS, sans chemin, identifiant, paramètres ni port personnalisé. L’adresse est propagée à la route frontend, au certificat frontend généré, à PUBLIC_BACKEND_URL et aux vérifications externes. Le TLS reencrypt et les services restent inchangés. OpenShift gère lui-même status.ingress.

    Par défaut, la gateway utilise gateway- suivi du nom d’hôte public. Pour une adresse distincte, fournir également :

    -UrlGateway 'wss://gateway-monprojet.pres.cluster.example'

    Cette adresse alimente la route gateway, son certificat, et PUBLIC_GATEWAY_URL. Lors d’une reprise, les adresses enregistrées sont conservées, même si les options ne sont pas répétées. Une adresse différente sur une installation existante est refusée : ce kit ne réalise pas une migration de domaine. -Reinstaller exige que le nettoyage ait été terminé ; il ne supprime pas l’installation à votre place. Un retrait complet peut supprimer les données PostgreSQL intégrées : ne pas l’utiliser pour une migration avec conservation des données.

    L’option ne contourne pas les droits OpenShift ni les règles DNS du client. Un domaine personnalisé peut être refusé à la création. Le choix du domaine .pres. reste à confirmer avec la plateforme ; l’option ne prouve pas que le domaine était la cause de l’erreur d’exposition.
