    Installer AppControl sur OpenShift avec PowerShell et oc¶

    Le parcours Windows recommandé : la commande oc déjà installée, un petit paquet de fichiers PowerShell et YAML, puis une seule commande de déploiement.

    OpenShift télécharge lui-même les images depuis le registre autorisé. Le paquet léger ne contient aucune image ni aucun exécutable. Il n’installe pas oc et ne modifie pas le PATH du poste. Aucun Helm, Docker, Python, WSL, OpenSSL ou outil de transfert d’images n’est nécessaire sur le poste client.

    Produit : AppControl 1.20.4. Paquet : Windows léger 1.20.4-1.

    1. Ce qui sera déployé¶

    PostgreSQL est inclus. Aucune base externe ni chaîne de connexion n’est à préparer pour cette première évaluation. Le script génère les identifiants, les certificats et la configuration de connexion, puis applique les objets OpenShift fournis. PostgreSQL utilise un volume persistant de 2 Gio.

    Dans le projet OpenShift dédié Rôle
    Interface web — 1 pod Le navigateur affiche les applications et les maps.
    Backend — 1 pod Gère les utilisateurs, les droits, les maps et les opérations.
    Gateway — 1 pod Relie les agents à AppControl et transmet les commandes. Elle est incluse.
    PostgreSQL — 1 pod + volume de 2 Gio Conserve les données AppControl. Accessible uniquement à l’intérieur du cluster.
    Agent de démonstration — 1 pod Exécute les commandes synthétiques de la map de test. Inclus par défaut dans ce parcours. 
    flowchart LR
  W["Poste Windows : PowerShell + oc existant"] -->|"appliquer les YAML"| O["API OpenShift"]
  R["Registre autorisé : Artifactory ou GHCR"] -->|"images téléchargées par les nœuds"| P
  subgraph P["Projet appcontrol-evaluation"]
    UI["Interface web"] --> B["Backend"]
    B --> DB["PostgreSQL + stockage 2 Gio"]
    G["Gateway"] --> B
    A["Agent de démonstration"] -->|"WSS via la Route gateway"| G
  end
  N["Navigateur"] -->|"HTTPS"| UI

    Cinq pods et cinq conteneurs en régime stable. Aucun Redis, fournisseur IA, serveur MCP ou service métier de la banque n’est requis. Une base PostgreSQL gérée par la banque est possible avec un autre profil du chart, mais ce parcours léger configure la base incluse.

    2. Les prérequis à obtenir une fois¶

    À préparer Ce qu’il faut concrètement
    Poste Windows Windows PowerShell 5.1, .NET Framework 4.8 et le oc déjà installé et approuvé par la banque. Scripts autorisés en mode PowerShell FullLanguage.
    Connexion Une connexion oc fonctionnelle au cluster du client, selon sa procédure habituelle.
    Projet Un projet dédié existant, par exemple appcontrol-evaluation, avec les droits de déploiement.
    Stockage Une StorageClass utilisable, par défaut ou nommée ; volume ReadWriteOnce de 2 Gio.
    Quotas Nœuds Linux AMD64. Pour les cinq pods : réservations totales de 1,15 vCPU et 992 Mio. Accepter aussi les limites des YAML et une marge pour les redémarrages.
    Registre Les cinq images accessibles par les nœuds, via Artifactory ou GHCR ; secret de lecture dans le projet si le registre est privé.
    Réseau et certificats Poste → API OpenShift et Route web HTTPS ; nœuds → registre ; échanges internes des services ; agent → Route gateway WSS 443. Les certificats des endpoints doivent être approuvés.
    Tunnel d’installation oc port-forward autorisé vers le projet : droit create sur pods/portforward et passage du tunnel par les éventuels proxies réseau. Pas de port entrant supplémentaire sur Windows.

    Le script ne crée pas le projet ni les accès au registre. Il ne requiert pas de compte administrateur Windows, de droit cluster-admin ni de SCC anyuid. Un projet dédié sépare les objets et les données ; il ne réserve pas à lui seul des nœuds physiques.

    3. Où sont les images et comment passe-t-on par Artifactory ?¶

    La release publique XComponent distribue les scripts, les YAML et les rapports. Son téléchargement ne demande pas de compte GitHub. Le dépôt de code, le site de livraison et le registre d’images sont trois choses différentes.

    Les cinq images officielles sont dans le registre GitHub GHCR, sous :

    ghcr.io/xcomponent/appcontrol-backend
ghcr.io/xcomponent/appcontrol-frontend
ghcr.io/xcomponent/appcontrol-gateway
ghcr.io/xcomponent/appcontrol-postgresql
ghcr.io/xcomponent/appcontrol-agent

    Ces packages XComponent sont privés au 31 octobre 2026. L’adresse seule ne suffit pas : leur lecture demande un accès autorisé. Le fichier images.lock.json du paquet fixe leurs empreintes SHA-256 ; le script n’utilise pas un tag latest susceptible de changer.

    Chez le client : Artifactory récupère les images¶

    C’est le fonctionnement de proxy envisagé :

    flowchart LR
  O["OpenShift"] -->|"demande l’image"| A["Artifactory de la banque"]
  A -->|"récupère une image absente du cache"| G["GHCR XComponent"]

    L’équipe plateforme configure un dépôt Docker distant vers GHCR, éventuellement exposé par un dépôt virtuel. Elle fournit l’adresse Docker de lecture, telle qu’indiquée par « Set Me Up », avec le chemin qui conserve le nom des images. Ce n’est pas l’adresse de l’interface web Artifactory.

    Deux accès sont distincts :

    • Artifactory → GHCR : compte autorisé à lire les packages XComponent et jeton GitHub avec le droit read:packages, configurés par la plateforme.
    • OpenShift → Artifactory : accès de lecture de la banque, généralement fourni par un secret d’images déjà créé dans le projet.

    Le poste Windows ne télécharge ni ne pousse les images. Il n’a pas besoin d’un compte d’import dans Artifactory. Le cache Artifactory se remplit à la demande ; il faut donc autoriser son accès amont ou faire précharger les cinq images par la plateforme. Un miroir interne alimenté par l’équipe plateforme convient également, à condition de conserver les digests.

    Références : dépôts Docker JFrog, cache distant JFrog, authentification GHCR.

    À obtenir de la plateforme : le préfixe Docker de lecture des images, le nom éventuel du secret de lecture dans le projet et la confirmation que les cinq images sont récupérables avec leurs empreintes. Exemple fictif : registry.banque.example/ghcr/xcomponent. Le script y ajoute /appcontrol-backend@sha256:…, et de même pour les quatre autres images. Si la plateforme utilise une autre organisation des chemins, préparer un verrou adapté avant le créneau ; ne pas inventer une URL de proxy.

    Si le cluster accède directement à GHCR¶

    Utiliser les références XComponent par défaut et un secret de lecture GHCR préparé dans le projet. L’identifiant GitHub et le jeton ne sont pas à écrire dans le script, les YAML ni l’historique PowerShell. Aucun mot de passe n’est inclus dans le livrable.

    4. Télécharger les petits fichiers de déploiement¶

    • Paquet Windows léger — scripts et YAML
    • Empreinte SHA-256

    Le ZIP est uniquement un moyen pratique de transporter les fichiers texte. Après téléchargement ou transfert approuvé, vérifier l’archive dans PowerShell :

    $archive = 'appcontrol-openshift-windows-light-1.20.4-1.zip'
$attendu = ((Get-Content "$archive.sha256" -Raw).Trim() -split '\s+')[0]
if ((Get-FileHash $archive -Algorithm SHA256).Hash -ne $attendu) {
    throw 'Empreinte incorrecte : ne pas utiliser cette archive.'
}

    Utiliser Extraire tout dans l’Explorateur. Ouvrir le dossier contenant Deployer-AppControl.ps1, taper powershell dans la barre d’adresse, puis Entrée. Le dossier manifests contient le YAML OpenShift consultable avant installation. Les autres fichiers PowerShell sont les fonctions utilisées par le script ; ce ne sont pas des logiciels supplémentaires à installer.

    5. Lancer avec la connexion oc déjà utilisée au client¶

    Vérifier la connexion habituelle :

    oc whoami
oc project appcontrol-evaluation

    Si le projet n’existe pas encore et que la plateforme autorise sa création, le créer d’abord avec oc new-project appcontrol-evaluation.

    Avec Artifactory, remplacer les deux valeurs d’exemple par celles fournies par la plateforme :

    .\Deployer-AppControl.ps1 -Projet appcontrol-evaluation `
  -Registre 'registry.banque.example/ghcr/xcomponent' `
  -SecretImages 'lecture-artifactory'

    Si le registre interne autorise la lecture sans authentification, omettre -SecretImages. Avec un accès direct à GHCR XComponent :

    .\Deployer-AppControl.ps1 -Projet appcontrol-evaluation -SecretImages 'lecture-ghcr'

    Ajouter -ClasseStockage 'nom-fourni-par-la-plateforme' uniquement si la classe par défaut ne convient pas. L’assistant affiche le serveur, le projet et les images ciblés avant confirmation. Il utilise une copie privée de la connexion ; il ne remplace pas le oc ni les paramètres de connexion habituels du poste.

    Le script effectue dans l’ordre : vérification des droits et des fichiers, préparation des secrets et certificats, traitement local du Template YAML avec oc process, application avec oc apply, attente des services, enrôlement de la gateway, puis création de l’agent et recette de la map de démonstration. Les nœuds OpenShift téléchargent les images.

    La recette redémarre la gateway, le backend et PostgreSQL pour vérifier les reconnexions et la conservation des données. Utiliser un projet d’évaluation isolé. Pour installer uniquement les quatre services, ajouter -SansDemo.

    6. Ouvrir et tester AppControl¶

    Le script affiche l’URL de l’interface et le chemin privé des identifiants administrateur. Le dossier d’état se trouve par défaut sous %LOCALAPPDATA%\AppControl\Installations, avec des droits limités à l’utilisateur Windows et au système. Ne pas envoyer ce dossier avec un rapport.

    Dans le navigateur, ouvrir l’application Qualification dependencies… indiquée par la recette. Elle comporte deux composants synthétiques :

    Action Ce que l’on constate
    Start All database-probe démarre, puis api-probe ; les deux passent au vert.
    Stop All L’API s’arrête d’abord, puis sa dépendance.
    Historique Les commandes exécutées et leurs résultats sont visibles.

    Les commandes sont des touch, test -f et rm sur des marqueurs dans /tmp du pod agent. Le démarrage de api-probe vérifie le marqueur de database-probe. Ce ne sont ni la vraie base PostgreSQL d’AppControl ni des services de la banque. Aucune commande métier n’est exécutée sur le poste Windows.

    Les cinq pods et la map restent disponibles après fermeture de PowerShell. L’agent de qualification est temporaire : son identité est conservée tant que son pod existe. Après remplacement de ce pod, relancer la recette crée un nouvel agent et une nouvelle map ; utiliser la nouvelle map indiquée. Un agent durable doit conserver son dossier d’identité sur un stockage persistant.

    Reprendre et diagnostiquer¶

    Conserver le dossier privé et reprendre avec les mêmes projet, nom et options indiqués par le script. Pour reprendre les services en conservant la map et l’agent existants, ajouter -SansDemo. Sans cette option, la recette crée une nouvelle démonstration. Le script refuse d’écraser une installation Helm ou des objets qui ne lui appartiennent pas.

    Symptôme Vérification
    oc absent ou connexion expirée Utiliser le CLI approuvé du poste et renouveler la connexion habituelle. Le script n’installe pas un autre CLI.
    Script bloqué par Windows Faire approuver les fichiers par l’équipe poste de travail ; ne pas désactiver la politique d’exécution.
    Secret d’images absent Faire créer le secret de lecture dans le bon projet.
    ImagePullBackOff Chemin exact de l’image, droits OpenShift → registre, droits Artifactory → GHCR et confiance TLS des nœuds.
    Volume Pending StorageClass, capacité et quota du projet.
    Tunnel d’installation refusé Droit pods/portforward et passage du tunnel par le proxy vers l’API.
    Ressource existante refusée Vérifier le projet et le nom choisis ; reprendre avec le dossier privé d’origine, sans forcer l’écrasement.

    Qualification et suite du POC¶

    Les preuves de la release précisent le paquet exact exécuté, Windows/PowerShell, les références d’images et les contrôles réalisés. Les images de ce parcours ont les mêmes digests que celles de la release 1.20.4. Le test du parcours léger doit être distingué de celui de l’ancien kit hors ligne : les images sont cette fois récupérées par le cluster et aucun Helm n’est appelé sur le poste client.

    Le registre Artifactory, les certificats et les règles réseau de la banque restent à valider dans son environnement. La préparation de ces accès conditionne le délai ; on ne peut pas promettre quelques minutes avant leur validation.

    Ce profil est mono-instance. Le SSO, la PKI bancaire, la sauvegarde/restauration, la base externe et la haute disponibilité se cadrent ensuite. Les certificats de service générés durent 90 jours et le jeton de gateway 30 jours ; le renouvellement reste explicite.

    La gateway incluse permet aussi de raccorder un agent extérieur via sa connexion sortante WSS 443 : suivre la procédure d’enrôlement.

    Pour un environnement qui impose de transporter les images sans accès à un registre amont, le kit hors ligne reste une option distincte. Ce n’est pas le parcours recommandé ci-dessus.
